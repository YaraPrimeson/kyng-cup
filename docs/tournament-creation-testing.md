# Проверка создания турниров

Дата: 28 октября 2026 года.

Форма `app/admin/create-tournament.tsx` вызывает `create_tournament_setup`.
Этот запрос проверяет доступ организатора и входные данные, создаёт турнир,
пары, группы, круговые матчи, сетку плей-офф и запись аудита в одной транзакции.
Функция `buildTournamentSetup` используется самой формой и тестами: проверки
выполняют реальную подготовку запроса, а не ищут строки в исходном коде.

## Быстрый запуск

```sh
npm run test:setup
```

73 проверки подготовки формы, импорта и распределения пар. База и учётная
запись не нужны. Дополнительно перебираются все допустимые сочетания числа
пар 2–64 и групп 1–26, в которых каждой группе достаётся минимум две пары.

```sh
npm test
npm run lint
```

`npm test` также собирает приложение и проверяет HTML основных страниц:
всего 79 тестов. SQL-проверки в эту команду не входят.

## Проверка базы

`tests/tournament-creation.sql` содержит 90 сценариев. Выполнить целиком в
Supabase SQL Editor либо через соединение PostgreSQL с правами `postgres`:

```sh
psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -f tests/tournament-creation.sql
```

Нужна база с миграциями проекта. Скрипт создаёт синтетические учётные записи
с адресами `@example.invalid` и уникальными идентификаторами. Вызовы создания
выполняются под ролями `authenticated` и `anon`, а не с обходом проверки доступа.
Все тестовые записи, временные функции и таблицы откатываются. Чужие турниры
и аккаунты не используются как тестовые данные. При ошибке скрипт сообщает
все провалившиеся сценарии и прерывается; `psql` закрывает соединение с откатом.
При ручном выполнении в постоянном соединении после ошибки выполнить `rollback;`.

| Область | Сценарии и проверяемый результат |
| --- | --- |
| Основная матрица | Теннис и падел × черновик и публикация × плей-офф и группы → плей-офф × 2, 7, 16, 64 пары: 32 сценария |
| Данные | Название, адрес, локация, даты, тип спорта, статус, число участников и места в сетке сохраняются |
| Пары | Посев, заполнители имён, введённые имена, Unicode и удаление пробелов |
| Группы | Ручные составы 3+5, одна группа, 26 групп, разное число выходящих, ноль выходящих из отдельной группы |
| Матчи | Круговой турнир внутри группы, правильные соперники, связи раундов и пустой плей-офф до выбора квалификантов |
| Пропуски в сетке | 3, 5, 6, 9, 13, 14, 17, 31, 33, 63 пары: продвижение только через действительно пустую ветку |
| Ошибочные данные | 38 сценариев: пределы размеров, пустые/неверные массивы, даты, адрес, спорт, статус, имена, составы и выходящие |
| Доступ | Новый одобренный организатор без прежних турниров, второй организатор, обычный, ожидающий, отозванный и анонимный доступ |
| Публикация | Гость видит опубликованный турнир и пары, но не черновик |
| Целостность | Дубли адресов отвергаются, ошибочные запросы не оставляют турнир, создатель получает членство и запись аудита |

## Найденные ошибки и результат

1. **Нельзя создать сетку на две пары.** Форма и функция `next_bracket_size`
   поддерживают два участника, но ограничение `tournaments_bracket_size_check`
   разрешает только 4, 8, 16, 32, 64. Это также мешает создать групповой турнир
   с двумя квалификантами. В действующей базе: **81/90 успешно, 9/90 падают**
   по этой общей причине. Подготовлена миграция
   `20261028163528_allow_two_pair_brackets.sql`, добавляющая размер 2.
   С ней **90/90 успешно**: изменение ограничения и весь набор тестов были
   выполнены в одной транзакции с последующим откатом. Постоянно в рабочую
   базу миграция в рамках этой проверки не применялась.

2. **Пустая колонка игрока при импорте могла пропасть.** Строка
   `Название команды<TAB>Первый игрок<TAB>` превращалась в две колонки после
   удаления пробелов всей строки. Название команды становилось первым игроком.
   Исправлено сохранением табуляции по краям строки. Тесты проверяют и пустого
   первого/второго игрока, и допустимое пустое название команды.

Локальная сборка и все 79 тестов проходят. ESLint проходит с двумя
предупреждениями об изображениях в неизменённом `app/profile/page.tsx`.
Общая проверка `tsc --noEmit` сообщает ошибки в `app/analytics.tsx` и
отсутствующие типы Cloudflare/Deno; эти файлы в данной работе не изменялись.

## Что остаётся ручной проверкой интерфейса

Автотесты покрывают подготовку запроса и реальное выполнение функции в базе.
Действия в браузере, сеанс входа и сетевые ошибки здесь не автоматизированы.
Для проверки интерфейса использовать тестовый черновик:

1. Войти организатором и открыть «Новый парный турнир»: исходно 16 пар,
   четыре группы по четыре пары, восемь выходящих, статус «Черновик».
2. Изменить число пар, добавить и удалить строку; убедиться, что составы
   и число групп пересчитываются, а заполненные имена остаются.
3. Вставить список, применить его, переместить пары вручную и повторно
   распределить равномерно. Попробовать сделать группу из одной пары:
   создание должно стать недоступным с понятным сообщением.
4. Переключить «Группы → плей-офф» на «Только плей-офф» и обратно.
   Проверить дополнительные настройки адреса, даты окончания и видимости.
5. При сохранении проверить блокировку полей и повторного нажатия;
   после успеха должен открыться созданный турнир.
6. В тестовом окружении отключить сеть: показать ошибку, сохранить введённые
   данные и позволить повторить запрос. Проверить конфликт занятого адреса.
